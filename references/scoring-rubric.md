# 判定标准与加权评分

## 三档维度判定

每个维度只允许三档结论，必须能落到具体情境上，禁止"还行""看情况"这类模糊表述。

| 判定 | 符号 | 含义 | 触发条件 |
|---|---|---|---|
| 匹配 | ✅ | 用户偏好与游戏实际情况一致 | 用户明确表达正向偏好，且该偏好正是游戏强项；无未解决顾虑 |
| 部分匹配 | ⚠️ | 可接受，但存在需要用户主动适应的摩擦 | 需要让步、妥协、额外学习成本，或该维度用户未充分表达（信息不足） |
| 冲突 | ❌ | 结构性不匹配，需要用户改变习惯才可能玩下去 | 用户明确说"不能接受"，或游戏强制要求与用户硬约束直接对立 |

**判定纪律**

- 用户没说清的维度记 `⚠️ 部分匹配` 并注明"信息不足"，**不要猜成 ✅**。
- 一票冲突与多票冲突要区分：`values`（底线/现实压力）与 `core_loop`（根本玩法不对味）属**关键维度**，其冲突优先级最高。
- 不允许因为"总体感觉不错"就把某个明确冲突项写成部分匹配。

## 权重

| 维度 | key | 权重 |
|---|---|---|
| 核心玩法类型 | `core_loop` | 2 |
| 挑战类型 | `challenge` | 2 |
| 操作难度 | `controls` | 1 |
| 游戏节奏 | `pace` | 1 |
| 社交需求 | `social` | 1 |
| 内容消耗 | `content` | 1 |
| 沉浸感来源 | `immersion` | 1 |
| 时间投入 | `time_budget` | 1 |
| 时间成本 | `time_cost` | 1 |
| 硬件要求 | `hardware` | 1 |
| 付费模式 | `payment` | 1 |
| 社区氛围 | `community` | 1 |
| 更新频率 | `update` | 1 |
| 情感体验 | `emotion` | 1 |
| 长线留存 | `retention` | 1 |
| 价值观契合 | `values` | 2 |

权重理由：核心玩法与挑战类型决定"玩不玩得下去"，价值观契合决定"能不能安心玩"，其余维度是摩擦项，可通过习惯调整消化。

## 计算公式

```text
得分   = Σ(该维度权重 × 判定系数)     判定系数：匹配 = 1.0，部分匹配 = 0.5，冲突 = 0
满分   = Σ(已问维度的权重)
适配率 = 得分 / 满分 × 100%
```

**只统计本次实际问过的维度**。跳过的维度不进分母，避免用户跳过的问题拉低结论。

## 结论分级

| 结论 | 条件 | 行动建议 |
|---|---|---|
| **高适配** | 适配率 ≥ 80%，且**无关键维度冲突**（`core_loop` / `challenge` / `values` 均非 ❌） | 推荐直接试玩或购买；给出入手方式（试玩版、免费周末、二手盘、云游戏试机） |
| **中适配** | 适配率 55%–79%；或适配率 ≥ 80% 但存在 1 个非关键维度冲突且用户愿意调整 | 建议先体验试玩版 / 看 3 篇以上不同立场的评测 / 等打折；给出 1 个低成本验证动作 |
| **低适配** | 适配率 < 55%；或存在 ≥ 2 个关键维度冲突；或存在 1 个无法回避的关键冲突（如价值观硬底线、硬件不达标且不升级） | 提醒潜在痛点，避免浪费资源；给出替代方向（同类但更契合其偏好的游戏类型特征） |

**强制覆盖规则**：即使适配率 ≥ 80%，只要出现以下任一情形，结论**不得**为高适配：

- `values` 为 ❌（涉及底线或会带来现实关系压力）；
- `core_loop` 为 ❌（根本玩法不对味）；
- 用户明确表示"每月预算有限"而 `payment` 为 ❌；
- 用户明确"每天只能 30 分钟以内"而 `time_budget` 为 ❌。

此时最高给"中适配"，并在报告首屏直说这是被哪一项压下来的。

## 风险点排序

"最需要留意的 3 点"按以下优先级取：

1. 关键维度冲突（`core_loop`、`challenge`、`values`）
2. 权重高的维度冲突（权重 2 优先）
3. 其余冲突
4. 有明确适用条件、需要用户主动适应的部分匹配项
5. 信息不足项（措辞用"需你确认"，而非"风险"）

不足 3 项时有几项写几项，**不要为凑数把匹配项包装成风险**。
